# Cap FPS 瞬时下降分析

## 问题描述

即使修复了 grab 线程的调度问题，在 `--capture-fps 50` 的设置下，仍然会观察到瞬时的 cap_fps 下降。

## 数据分析

从实际运行报告 (`/tmp/layered-live-runtime-report.json`) 分析：

### 关键指标
- **总运行时间**: 33 秒
- **总抓取帧数**: 1390 帧
- **平均 FPS**: 42.1 fps (1390 / 33)
- **目标 FPS**: 50 fps
- **Slot 饥饿事件**: 仅 1 次

### 性能瓶颈

1. **屏幕捕获耗时**:
   - 总耗时: 24142 ms
   - 操作次数: 1390
   - **平均每次: 17.37 ms**

2. **内存拷贝耗时**:
   - 总耗时: 5945 ms
   - 操作次数: 1389
   - **平均每次: 4.28 ms**

3. **单帧总耗时**:
   - grab + copy = 17.37 + 4.28 = **21.65 ms**
   - 对应最大 FPS = 1000 / 21.65 = **46.2 fps**

## 根本原因

### 1. 硬件性能限制

**屏幕捕获 API 性能**:
- MSS 库调用 macOS 的屏幕捕获 API
- 单次 `sct.grab()` 需要 ~17ms
- 这是操作系统和硬件的固有限制

**内存带宽限制**:
- 拷贝 BGRA → RGB 到共享内存需要 ~4.3ms
- 对于 1920x1080 的屏幕，每帧约 6MB 数据
- 内存带宽: 6MB / 4.3ms ≈ 1.4 GB/s（合理的内存拷贝速度）

### 2. 处理时间超过目标间隔

- **目标间隔**: 50 fps = 20 ms/frame
- **实际耗时**: 21.65 ms/frame
- **结果**: 每帧都会落后 1.65ms，无法维持 50 fps

### 3. 瞬时 FPS 波动的原因

即使平均 FPS 稳定在 42 fps，瞬时 FPS 仍会波动，原因包括：

**a) 处理时间方差**:
- 屏幕捕获时间: 10-30ms（取决于系统负载）
- 内存拷贝时间: 3-6ms（取决于内存带宽竞争）
- 这导致帧间隔不均匀

**b) 系统级干扰**:
- **Python GC 暂停**: 通常 1-5ms，偶尔 10-50ms
- **OS 线程调度**: 上下文切换、优先级反转
- **其他进程竞争**: CPU/内存带宽被其他进程占用

**c) 追赶行为**:
- 当处理超过 frame_interval 时，下一次捕获立即开始（无 sleep）
- 这会创建"快速捕获突发"后跟"较慢周期"的模式
- 瞬时 FPS 测量会显示为下降

## 优化方案

### 已实现的优化

1. **Deadline 驱动调度** ([workers.py:298-378](../src/screen_airdrop/receiver/runtime/workers.py#L298-L378)):
   - 非阻塞 slot 获取
   - 始终在 deadline 时捕获，无论 slot 是否可用
   - 当落后时立即开始下一次捕获

2. **改进的追赶逻辑**:
   ```python
   # 当处理时间超过 frame_interval 时，立即开始下一次捕获
   next_deadline += frame_interval
   now_after = time.perf_counter()
   if now_after >= next_deadline:
       next_deadline = now_after
   ```

### 推荐配置

根据硬件限制，推荐的 FPS 设置：

1. **保守配置** (稳定优先):
   - `--capture-fps 30`
   - 单帧预算: 33.3ms
   - 实际耗时: 21.65ms
   - 余量: 11.65ms (35%)

2. **平衡配置** (推荐):
   - `--capture-fps 40`
   - 单帧预算: 25ms
   - 实际耗时: 21.65ms
   - 余量: 3.35ms (13%)

3. **激进配置** (最大吞吐):
   - `--capture-fps 50`
   - 单帧预算: 20ms
   - 实际耗时: 21.65ms
   - **超出预算**: -1.65ms
   - 实际 FPS: ~42-46 fps

### 未来优化方向

要进一步提升性能，需要更深层的架构改动：

1. **异步内存拷贝**:
   - 将内存拷贝移到单独的线程/进程
   - Grab 线程只负责捕获，立即返回
   - 需要双缓冲机制

2. **零拷贝捕获**:
   - 直接将屏幕捕获到共享内存
   - 需要修改 MSS 库或使用更底层的 API
   - 可节省 4.3ms 的拷贝时间

3. **GPU 加速拷贝**:
   - 使用 CUDA/Metal 进行内存传输
   - 可能将拷贝时间降低到 1-2ms
   - 需要 GPU 支持和额外依赖

4. **批处理**:
   - 一次捕获多帧再批量拷贝
   - 增加延迟但提高吞吐量
   - 适合离线处理场景

## 监控指标

要诊断 FPS 问题，关注以下指标：

1. **raw_grab_fps**: 实际捕获速率（应接近硬件上限）
2. **capture_grab_time_ms / capture_grab_ops**: 平均捕获时间
3. **capture_copy_time_ms / capture_copy_ops**: 平均拷贝时间
4. **slot_starvation_events**: Slot 饥饿次数（应 < 1%）

## 结论

**瞬时 FPS 下降是正常现象**，原因是：

1. **硬件限制**: 单帧处理时间 (21.65ms) 超过 50 fps 的目标间隔 (20ms)
2. **系统抖动**: GC、调度、资源竞争导致处理时间波动
3. **追赶行为**: 当落后时立即捕获，创建不均匀的帧间隔

**当前实现已经是最优的调度策略**，进一步提升需要：
- 降低目标 FPS（推荐 30-40 fps）
- 或实施更深层的架构优化（异步拷贝、零拷贝等）

**平均 FPS (42.1) 已经非常接近硬件上限 (46.2)**，说明调度效率很高。
